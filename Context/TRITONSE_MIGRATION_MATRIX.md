# TritonSE Migration Matrix

## Purpose

This matrix translates the approved Option B decision into concrete migration boundaries. The legacy TritonSE repository remains a product and interaction reference; it is not the base application. No legacy source file should be copied into the new foundation merely because it already exists.

The treatment labels mean:

- **Reuse directly** — copy an approved static asset or non-executable artifact without changing its behavior. Confirm ownership and attribution first.
- **Adapt** — preserve the product concept, content, or interaction, but implement it against the new architecture and current website contracts.
- **Rewrite** — replace the implementation. Legacy code may be read for intent, but should not enter the new codebase.
- **Defer** — keep outside the foundation and initial feature scope until the nonprofit prioritizes it and its dependencies are ready.

## Executive migration boundary

| Treatment      | Summary                                                                                                                                                     |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reuse directly | Approved visual assets, chess-piece images, brand marks, and required license notices only.                                                                 |
| Adapt          | Role-aware navigation, lesson progression concepts, chess interaction behavior, and product language.                                                       |
| Rewrite        | Application shell, screens, authentication, API client, state, sockets, chess synchronization, progress persistence, styles, backend prototypes, and tests. |
| Defer          | Full chat/mentoring, invitations and advanced game lifecycle, meetings, notifications, offline support, analytics, and other non-MVP features.              |

## Rewrite

These implementations are incompatible with the selected architecture or contain correctness/security risks.

| Area                                         | Legacy evidence and reason                                                                                                                                                         | Rewrite target                                                                                                                                                                                                             |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application scaffold and build configuration | `YSC-Mobile-Application/package.json` is based on Expo 47, React Native 0.70.5, TypeScript 4.6.3, and an old native dependency set.                                                                | A clean, currently supported Expo TypeScript project created in its own reviewed PR after the plan is approved.                                                                                                            |
| Navigation implementation                    | `YSC-Mobile-Application/src/components/Navigator.tsx:45-150` mixes session state, roles, socket behavior, tabs, and feature stacks.                                                                | File-based Expo Router layouts with route groups, guarded layouts, stable Stack/Tabs primitives, and feature-independent placeholders.                                                                                     |

## Defer

Deferral means “not part of the foundation,” not “discard forever.” Each item should become a separately scoped feature after product and infrastructure decisions are made.

| Feature                                                           | Why deferred                                                                                                         | Entry condition                                                                                                      |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Full mentor/student chat                                          | Child safety, moderation, retention, identity, and real-time reliability must be agreed first.                       | Written safety/data policy, authenticated protocol, moderation owner, and feature acceptance criteria.               |
| Mentor presence and manual mentor selection                       | Requires reliable presence, capacity, availability, and matching semantics.                                          | Nonprofit defines the operating model and the backend exposes authoritative availability.                            |
| Invitations, draw offers, resign, rematch, clocks, and spectators | These enlarge the chess state machine and reconnect surface.                                                         | Basic server-authoritative game creation, legal moves, completion, and recovery are proven first.                    |
| Voice/video meetings or Agora                                     | Website configuration mentions Agora, but the mobile experience, privacy, and account ownership are not established. | Explicit product requirement, current credentials/account owner, privacy review, and native-development-build spike. |
| Stockfish analysis/opponent                                       | The website documents separate Stockfish infrastructure; mobile requirements and operating cost are unclear.         | Mode, difficulty, latency, hosting, rate limits, and API contract are approved.                                      |
| Badges, streaks, and analytics dashboards                         | Website routes exist, but they are not necessary to prove the mobile foundation.                                     | MVP prioritization and stable progress/activity contracts.                                                           |
| Signup and password recovery                                      | The current mobile prototype does not supply a safe complete flow, and backend policy is unclear.                    | Nonprofit chooses mobile self-service versus website/admin provisioning and defines recovery security.               |
| Push notifications                                                | Requires messaging accounts, permission UX, privacy decisions, and backend device-token lifecycle.                   | Concrete notification use cases and account ownership are approved.                                                  |
| Offline lessons or games                                          | Conflict resolution and content caching add substantial complexity.                                                  | Explicit offline requirement, cache policy, and server reconciliation design.                                        |
| Advanced observability/product analytics                          | Useful but vendor, consent, and budget are unconfirmed.                                                              | Vendor/account, event taxonomy, PII policy, retention, and consent requirements.                                     |
| Tablet/web layout and broad platform optimization                 | Supported device scope is unknown.                                                                                   | Target platforms, minimum OS versions, orientation, and accessibility targets are confirmed.                         |

## Migration acceptance rule

Before any legacy item is brought into a feature PR, the PR description should answer:

1. Which matrix row authorizes the treatment?
2. Is the source being copied, adapted as behavior, or only used as a reference?
3. What current website contract and Figma state does it match?
4. What licensing/attribution and accessibility checks apply?
5. Which tests demonstrate behavior without preserving legacy coupling?

If these questions cannot be answered, the default treatment is **rewrite or defer**, not direct reuse.
